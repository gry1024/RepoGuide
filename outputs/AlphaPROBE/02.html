第2章：表达式与算子体系

像 LEGO 积木，Abs/Add/Sub/Mul/Div/TsMean/TsCorr 等算子是基础块，组合成复杂 alpha 表达式。

欢迎

上一章我们拿到了干净的三维行情张量，但 LLM 不会直接输出张量——它输出的是字符串，比如 Div(Sub($close, $open), Add(Sub($high, $low), 0.000001))。AlphaPROBE 需要一套机制把这些字符串解析成可求值的对象树，再在张量上算出因子值。本章拆解 src/alphagen/data/expression.py、tree.py、dimension.py 三件套：表达式类层次、AST 解析器、量纲计算器。它们共同定义了 AlphaPROBE 的表达式 DSL，是 LLM 生成与池验证的共用语言。

它解决什么问题？

alpha 表达式本质上是一种小型 DSL（领域特定语言）。它有「词法」（Feature、Constant、DeltaTime）和「语法」（一元/二元/滚动/成对滚动四类算子）。如果没有统一的表达式体系，LLM 生成的字符串就无法被验证、无法被求值、更无法被纳入知识图谱。更麻烦的是，AlphaPROBE 要求所有候选因子量纲为零（dimensionless）——因为只有无量纲的因子才能在不同股票、不同价位间横向比较。这就需要一套量纲推导规则，自动判断一个表达式是否可比。

类比 LEGO 积木：Abs、Add、TsMean、TsCorr 等算子是基础块，它们按固定接口（参数个数、类型）拼接，组合成复杂的 alpha 表达式。表达式体系既定义了积木块的形状，也定义了拼接规则，还提供了一把「量纲尺」量出成品是否合格。

核心设计思路

设计上有四个关键点。第一，抽象基类 Expression：所有表达式都实现 evaluate(data) 接口，统一返回张量，并用 Python 运算符重载（__add__ 等）让表达式可以用 Ref(close,-20)/close-1 这样自然的语法构造。第二，四类算子基类：UnaryOperator、BinaryOperator、RollingOperator、PairRollingOperator，每类有统一的构造与求值模板，新增算子只需实现 _apply。第三，RPN 解析器：ExpressionParser 把中缀字符串递归拆成逆波兰 token 序列，再由 ExpressionBuilder 在栈上组装成表达式树，每步都做合法性校验。第四，量纲递归推导：DimensionCalculator 按算子规则递归算出整棵树的量纲，Dim=0 才允许入池。

代码深入

Expression 抽象基类与叶子节点

Expression 是所有节点的根，定义了 evaluate 抽象方法和一组运算符重载。Feature 是行情特征叶子，evaluate 时从 data 张量切片；Constant 是常量叶子，evaluate 时广播成全零或全值张量。

四类算子基类 —— 拼接规则

Operator 派生出四类：UnaryOperator（一元）、BinaryOperator（二元）、RollingOperator（滚动）、PairRollingOperator（成对滚动）。每类的 evaluate 模板已实现好，子类只需实现 _apply。这里看前两类与滚动类的核心。

198    def evaluate(self, data: StockData, period: slice = slice(0, 1)) -> Tensor:
199        start = period.start - self._delta_time + 1  # start/stop 计算需要回看 dt 天的窗口
200        stop = period.stop
201        # L: period length (requested time window length)
202        # W: window length (dt for rolling)
203        # S: stock count
204        values = self._operand.evaluate(data, slice(start, stop))   # (L+W-1, S)
205        values = values.unfold(0, self._delta_time, 1)              # (L, S, W)  # unfold 把 (L+W-1, S) 展开成 (L, S, W) 便于向量化
206        return self._apply(values)                                  # (L, S)  # _apply 在窗口维 W 上归约，输出 (L, S)

RollingOperator 的第 199-206 行是最精妙的部分。时序算子（如 TsMean($close, 10)）需要回看 10 天，evaluate 先把请求区间扩展成 slice(start - dt + 1, stop)，递归求出 (L+W-1, S) 的历史张量，再用 unfold(0, dt, 1) 沿时间维滑窗展开成 (L, S, W)，最后由 _apply 在 W 维上归约（如 mean/std/max）。这种滑窗 unfold 让所有滚动算子都能向量化计算，避免了 Python 循环，是 AlphaPROBE 能快速求值海量表达式的性能基础。

ExpressionParser.parse —— 从字符串到表达式树

解析器把中缀字符串递归拆成逆波兰 token 序列，再交给 ExpressionBuilder 在栈上组装。tokenize 递归处理嵌套括号，split_arguments 正确处理逗号分隔的参数。

tree.py第 197-207 行
197    def parse(self, expr: str) -> Expression:
198        self.tokens = self.tokenize(expr)  # 先 tokenize 得到 RPN token 序列
199        # Create a new builder for each parse operation
200        builder = ExpressionBuilder()  # 每次 parse 创建新 builder，避免状态污染
201        for token in self.tokens:
202            builder.add_token(token)  # 逐个 add_token，在栈上组装表达式树
203        return builder.get_tree()  # 栈中应只剩一棵树，否则抛异常

ExpressionBuilder.add_token 在每个 token 入栈时都调用 validate 做合法性校验：例如 RollingOperator 要求栈顶必须是 DeltaTime（时间窗口），BinaryOperator 要求左右操作数不能都是 DeltaTime。这套校验保证了 LLM 生成的字符串即使语法合法，结构上也不能违反算子的参数契约——这是第 8 章验证流程的第一道关。

DimensionCalculator._dimension —— 量纲递归推导

量纲计算器按算子规则递归算出整棵树的量纲。Feature 量纲为 1，Constant 为 0，Add/Sub 取 max，Mul 取和，Div 取差，Rank/Sign/TsCorr 等归一化算子强制为 0。只有 Dim=0 的表达式才允许入池。

182            rhs = self._dimension(expr._rhs)  # type: ignore[attr-defined]
183            return lhs + rhs
184
185        if isinstance(expr, Div):  # Div 量纲取差（同量纲相除得 0，即可比）
186            lhs = self._dimension(expr._lhs)  # type: ignore[attr-defined]
187            rhs = self._dimension(expr._rhs)  # type: ignore[attr-defined]

189

第 185-188 行的 Div 规则是核心：两个同量纲的子表达式相除，量纲相减为 0，即得到无量纲因子。这就是为什么 AlphaPROBE 的初始表达式（见 train_new_work.py:21）几乎都是 Div(...) 形式——Div($high, $close) 的量纲是 1-1=0。prompt 里也明确要求 LLM 只生成 dimensionless 表达式（PROMPT_DIMENSION_REDUCTION），DimensionCalculator 则在代码侧兜底校验。

数据流

输入：LLM 生成的表达式字符串（如 Div(TsMean($close, %d), $close)）。内部：ExpressionParser.parse 递归拆解为 RPN token，ExpressionBuilder 在栈上组装成表达式对象树；DimensionCalculator.dimension 递归算量纲。输出：一棵可求值的 Expression 对象树，调用 expr.evaluate(data) 即得 (T, N) 因子张量。这棵树也会被知识图谱（第 4 章）tokenize 成节点 payload。

关联公式

量纲推导是一套代数规则，可与代码逐条对应：

$$\text{Dim}(\text{Div}(x,y)) = \text{Dim}(x) - \text{Dim}(y),\quad \text{Dim}(\text{Mul}(x,y)) = \text{Dim}(x) + \text{Dim}(y)$$
$$\text{Dim}(\text{Rank}(x)) = 0,\quad \text{Dim}(\text{TsCorr}(x,y,d)) = 0$$

只有 $\text{Dim}(\text{expr}) = 0$ 的表达式才被判定为「comparable」，允许进入候选池。这条约束贯穿 LLM prompt 与 DimensionCalculator 两处。

设计权衡

为什么用 RPN + 栈组装而不是直接递归下降？因为 RPN 天然消除括号与优先级歧义，且 ExpressionBuilder 的 validate 能在每个 token 入栈时即时校验参数契约，对 LLM 这种「不可信输入」友好——一旦某个算子参数不对，立刻抛 InvalidExpressionException，不会等到求值时才崩溃。代价是 tokenize 的递归实现稍复杂，但收益是验证的确定性与可解释性。

小结

表达式体系用「抽象基类 + 四类算子 + RPN 解析器 + 量纲计算器」定义了 AlphaPROBE 的 DSL。Expression 统一求值接口，算子基类用 unfold 实现向量化滚动，解析器在栈上做即时校验，量纲计算器用代数规则保证因子可比。下一章我们看这些表达式如何被评估出 IC/ICIR。
